# Hosting the web app on Netlify

The client already builds for the browser — `apps/mobile` produces Android and
web from one codebase, and the web export has been part of every check in this
repository since it existed. Nothing needed porting. What follows is the hosting
around it.

## What you get

`pnpm build:web` produces `apps/mobile/web-build/` — **4.1 MB**, 37 routes, each
static-exported as its own HTML file. Deep links work without a single-page
rewrite; only the six dynamic routes need one, and those are generated.

## Deploying

### Connected to the repository (recommended)

`netlify.toml` at the repo root already carries the build. In Netlify:

1. **Add new site → Import an existing project**, pick the repository.
2. Leave the build settings alone — `netlify.toml` sets base, command and
   publish directory. A pnpm monorepo needs the build to run from the repo
   root, which is why `base` is `.` and not `apps/mobile`.
3. Set one environment variable:

   | Key                   | Value                                |
   | --------------------- | ------------------------------------ |
   | `EXPO_PUBLIC_API_URL` | `https://fitnellisense.onrender.com` |

4. Deploy.

### One-off, from this machine

```bash
pnpm build:web
npx netlify deploy --dir apps/mobile/web-build --prod
```

## The step that is not optional

**Add the site's origin to `CORS_ORIGINS` on the API and redeploy it.** Until
you do, every request from the browser is refused and the app looks broken
while being perfectly healthy.

```
CORS_ORIGINS=https://ascension.netlify.app
```

Comma-separated for more than one. The API **refuses to start** with a wildcard
outside development, so this cannot be shortcut.

Then **open it in a browser and sign in.** The CORS test suite cannot catch a
real preflight failure — native Android sends no `Origin` header at all, so
every existing test passes against a configuration no browser would accept.
This is the one check that has to be done by hand, and CLAUDE.md says so.

Deploy previews each get their own origin and will be refused until added. That
is the right default: an allowlist that admits every preview admits anyone who
opens a pull request.

## Security headers

`_headers` and `_redirects` are **generated by the build**, not written by hand,
and land in the publish directory where Netlify reads them.

The Content-Security-Policy is the reason. On Android the session lives in
Keystore-backed storage; **on web there is no equivalent, so it lives in
localStorage** where any injected script could read it. A strict CSP is the
mitigation, and strict means no `script-src 'unsafe-inline'`.

Expo emits one inline bootstrap script per page. It is allowed **by SHA-256
hash**, computed from the export that was just built — so if Expo changes that
line, the policy follows it rather than silently blocking it and serving a blank
white page.

| Directive                                   | Value                           | Why                                                                                                          |
| ------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `script-src`                                | `'self'` + one hash             | No inline script but Expo's own bootstrap                                                                    |
| `style-src`                                 | `'self' 'unsafe-inline'`        | react-native-web injects its stylesheet at runtime. Unavoidable, and inline _style_ cannot read localStorage |
| `img-src`                                   | `'self' data: blob:` + jsDelivr | Exercise demonstration images are on the CDN (BRD §6.8)                                                      |
| `connect-src`                               | `'self'` + the API              | Nothing else is contacted from the browser                                                                   |
| `object-src`, `base-uri`, `frame-ancestors` | `'none'`                        | No embedding, no base-tag injection, no clickjacking                                                         |

`camera` is deliberately **absent** from `Permissions-Policy`, because the
barcode scanner needs it. `microphone`, `geolocation`, `payment` and `usb` are
all denied.

`scripts/check-web-headers.mjs` runs in CI immediately after the build and
fails if a hash is stale, if `unsafe-inline` creeps into `script-src`, or if a
dynamic route ships without its rewrite. It has been verified to exit non-zero
on a tampered policy — a check that cannot fail is not a check.

## What differs in a browser

| Feature                                       | Browser          | Note                                                                                                                                    |
| --------------------------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Logging, history, routines, insights, ranking | **Works**        | Identical to Android                                                                                                                    |
| Barcode scanning                              | **Manual entry** | `expo-camera`'s scanner does not fire on web, so the screen leads with the number field rather than showing a camera that never decodes |
| Rest-timer notification                       | **No**           | Already guarded; the in-app timer still runs while the tab is open                                                                      |
| Haptics, navigation sound                     | Silent / no-op   | Already guarded                                                                                                                         |
| Session storage                               | localStorage     | See the CSP note above                                                                                                                  |

## Two things worth doing before sharing the link

- **A custom domain.** `*.netlify.app` is fine for a trial. A real domain also
  lets the API's allowlist stop changing every time the site is renamed.
- **Update the privacy policy.** It currently names four processors. Netlify
  would be a fifth, and it sees visitors' IP addresses. The policy is
  `docs/privacy-policy.md`, served by the API, so it is one edit and a deploy.
